# 精简仓库

保留仍有用途或保留义务的仓库内容。把相关的代码、测试、文档和其他产物放在一起审查；文档和产物的清理不以代码或测试有改动为前提。清除有证据的冗余是为了减轻维护负担，不是为了完成删除指标。没有哪一类内容必须减少；找不到可以安全删除的内容也是有效结论。

## 确定范围与授权

查明请求指向的仓库或子树、明确排除的部分、权威的需求与政策、已接受的决定、已知的验证基线，以及实质性的缺口。

改动之前先核实候选项：

- **只审查**：报告发现，不修改，也不询问是否清理。
- **默认**：列出有证据且可执行的候选项，按批询问一次，不逐文件询问；没有候选项就不问。已知的配套改动放进同一批。获批的工作直接做完，不再重复询问；之后出现的、不在该批准范围内的候选项另行按批征求同意。已被排除的项不再提出。
- **直接清理**：用户明确要求直接清理时，范围内已纳入版本控制的内容中有证据的冗余可以不经常规确认直接处理，之后出现的候选项也一样。

两种写入模式下，删除未跟踪或被忽略的文件都需要覆盖这些文件的明确授权。默认模式下，把它们在同一批询问中单独列出。无权改动的内容予以保留；继续做与之无关且已获授权的工作并加以验证。

检查实现、调用方、测试、文档、配置、生成器、资产、脚本以及开发或交付入口之间的实际关系。依赖关系追到足以判断受影响的候选项为止，不把有界的请求变成无关的仓库重新设计。

现行契约来自实际生效的需求、政策和已接受的决定。现有实现是证据，不自动成为需求。历史上的假设和许可不能确立当前事实。

保全的是当前可观察的契约，不是每一个历史 API 或兼容路径。默认不保留向后兼容，并不构成改变现行契约的授权。拟议改动若会改变调用方能观察到的东西（如接受的输入、错误或副作用），报告差异和拟议结果，把它排除在普通清理之外；没有用户对该改动的明确授权，不实施这一行为变更。不借清理顺带确立或改写项目政策。

## 保全四类义务

一个候选项可能同时承担多种义务。按实际用途分类，不按文件名、扩展名、目录或是否由工具生成来分类。

| 内容 | 需要保全的义务 |
| --- | --- |
| 代码 | 现行行为和必要的复杂度：所需的输入、输出、错误、副作用、不变量，以及适用的运行时、数据、安全、隐私、并发或迁移约束。 |
| 测试 | 对有意义的回归的独有检测，包括相关边界、失败分支、并发条件和禁止的副作用。 |
| 文档 | 仍然有效的决定、约束、适用条件、假设、必要的出处、验收证据和尚未解决的验证缺口。保留需求、提案、观察和历史结果之间的区别。 |
| 其他产物 | 实际的开发、构建、运行、验证或交付消费者，以及许可、审计、可复现性和其他已确立的保留义务。 |

义务可以通过归并来保全，不必保留每一个原始文件。义务明确要求保留原件时，保留原件。

业务历史、迁移链、许可证、测试基准和必需的交付输入，不能仅仅因为陈旧或不是应用源码就视为可以丢弃。

## 找出候选项并给出依据

留意重复的行为或信息、已无人使用的消费者或输出、不可达的分支、被取代的路径、冗余的覆盖、过时的报告、非基准的截图、脚手架残留、已完成使命的过渡开关，以及不再有用途的生成产物。

这些是候选类别，不是删除规则。可以重新生成、由工具生成、属于历史或在文本搜索中找不到，都不足以作为删除的证据。

在上下文中打开决定性的证据。相关时检查动态注册、配置、打包、CI、生成器、运行路径、外部接口和有用的历史。把“尚未找到消费者”与“已确立没有用途或保留义务”区分开。

对每一组有意义的候选项，查明：

- 它当前的用途和适用的义务。
- 支持删除或归并的证据。
- 之后由哪里继续承担仍然存在的义务。
- 任何被明确解除的义务，以及解除它的已接受依据。
- 能支撑这一决定的验证，以及仍然存在的不确定性。

这份对应关系保持简短，不要求长期保存的清单或报告。未能解决的候选项继续调查或予以保留，不把它们当作已确认的冗余提出。

保留与否取决于仓库无法确立的事实（如部署状态、线上数据或客户端持有的记录）时，指出这一事实，并把受影响的候选项归为一组。只有答案会改变保留什么时，才把缺失的事实集中起来询问。实质性的不确定仍然存在时，保留内容。

## 精简相互关联的内容

### 代码

合并相似实现之前，比较调用条件、校验顺序、错误行为、状态变化、回滚和其他相关影响。

已经分化的实现若能在保全各自现行契约的前提下归并，按其他候选项同样的方式评估这一归并。

只被测试引用的生产成员是候选项，不是已确认的死代码。判断它是有意设置的测试接缝、应当归入测试的夹具，还是覆盖应当迁到现行路径上的被取代路径。

删除包装层、守卫、兼容路径或辅助函数之前，判断它是否承载独立的契约或必要的复杂度。

删除有其他值由它派生的字段或状态之前，追踪派生出的符号、接口和文案，不只追原来的名字。按范围决定它是否需要单独一批。

在有类型检查的代码库里删除字段时，先从它的契约类型中删除，用类型检查枚举有类型的位置。手写的 SQL 夹具、拒绝多余字段的严格运行时模式、翻译词典与动态键、浏览器测试和端到端测试要另行检查。文档既按标识符搜索，也按概念搜索。

删除取决于已存储数据的形态时，采用[持久化数据清理](references/persisted-data-cleanup.md)。

### 测试

比较前置假设、输入边界、失败分支、并发条件、断言和副作用检查。经过同一段代码，不等于具备同等的回归检测能力。

删除有效覆盖之前，找出保留下来的、能检测同样有意义的失败的断言，或把独有的断言迁入合适的测试。不要假定更高层的测试包含了更低层的测试或性质测试的覆盖。测试的前置准备依赖某个被删除的状态时，如果同一契约在新数据上仍可观察，就改前置准备；只有契约不再适用时才删除测试。

把脆弱的实现细节断言和一次性的清理检查与持久的契约区分开。拒绝路径和禁止的副作用可能提供必不可少的负向覆盖。收紧约束之后，重新检查每一个预期的拒绝，确保它是因为预期的原因失败。

### 文档

归并重复的信息、撤下过时的材料，同时给仍然成立的事实和决定一个合适的权威位置。

删除文档之前，核实其中独有且仍然有效的信息和必要的历史背景已经带到别处。保留尚未解决的验收缺口，不把过去的部分结果改写成现在的完成声明。

`AGENTS.md` 和贡献指南的规则按实际生效的约束去重，不按措辞。删除某一条款或整个冗余的子级文件之前，检查受影响路径在改动前后的实际加载、适用范围和优先级。共享的 Agent 规则留在根 `AGENTS.md`、项目政策留在贡献指南，只要那里是它们的权威位置。为保全约束，在需要的地方保留一条简短的操作规则或一个有效的引用。

- 删除主题在仓库中已不存在的规则。来自 repo-craft [根规则模板](../maintain-agent-rules/references/AGENTS.template.md)或[贡献指南模板](../maintain-project-docs/references/CONTRIBUTING.template.md)的条款例外：不因其主题当前不存在而删除，只去除真正的重复。
- 声明的条件或范围不同，只有在改变实际生效的约束时才算数。较窄的条款若删去后在其范围内仍有同样的要求生效，可以是冗余的。只有适用的要求相互重叠且不相容时才报告冲突。
- 不因为某条仍然适用的规则看似多余，或因为用户级指令文件也写了它，就把它删掉。

[项目文档维护](../maintain-project-docs/SKILL.md)固定结构中的零字节占位文件和空的 `docs/adr/` 目录，不因为是空的而删除。

修复受影响的导航、链接、锚点和交叉引用。不要仅仅为了完成清理而重建文档体系、强加一套文档集合或改写项目政策。

用户明确要求文档描述现状而不是工作的历史时，另外采用[现状文档清理](references/current-state-cleanup.md)。

### 其他产物

删除资产、截图、报告、生成文件、配置、依赖或脚本之前，检查实际的消费者和保留义务。

把由操作人员运行的工具追溯到实际的工作流，如初始化、发布或恢复。仓库里没有引用或文档，不能证明它冗余。有外部使用的具体迹象时，查阅可以访问的操作手册或其他证据。不要为每一个没有引用的脚本穷尽搜索假想的外部使用者。

对截图，区分可丢弃的截取、对比基准、必需的证据和文档资产。对生成文件，区分可以重新生成的中间产物与必须入库的构建或交付输入。

配套的夹具、辅助代码、依赖、脚本和引用，在其剩余用途确实消失时一并清理。

## 验证四项保全责任

既审查留下来的内容，也审查被删除的材料：

- **行为**：现行契约和必要的复杂度仍然得到实现。
- **覆盖**：保留的测试仍能检测到被删除或归并的测试所保护的有意义的回归。
- **知识**：有效的决定、约束、适用条件和验收缺口仍然得到准确表述。
- **消费者与保留**：必需的工作流、产物和已确立的保留义务仍然得到支持。

把生产逻辑和对应的断言一起删掉，不会仅仅因为剩下的测试套件通过就证明安全。同样，链接有效不能证明信息已完整迁移，能成功重新生成也不能证明某个产物原本不需要。

采用已知基线，需要时检查改动前的相关行为以解读结果。选择与受影响义务相称的检查，并运行仓库要求的验证。要靠缓慢的浏览器或端到端测试套件判断改动时，在动手修改之前先跑一遍以建立基线。

受影响的代码用行为测试，覆盖替换用断言级审查，文档用内容和链接检查，产物用相关的消费者或打包检查。不要为一处孤立的文字改动强加无关的应用测试，也不要设置统一的覆盖率或变异测试门槛。

选择补救办法之前，先查明失败属于产品回归、测试脆弱、工具缺陷还是环境限制。与基线比较，并把失败的断言追溯到受影响的代码（包括间接影响），以区分既有的失败和新的回归。之后的修改会使受影响的验证证据失效。

一次性的删除和引用清理用临时检查。不保留只为证明这次清理发生过的永久测试。持久的行为或兼容性约束仍然是正当的测试。

对照所有受影响的义务类别审查最终的合并差异。检查通过和删除数量可以佐证这一审查，但不能代替它。

## 迭代到精简基线

在写入模式下，重复候选发现、义务与消费者检查、已获授权的清理和验证。每一轮验证通过后，检查由改动暴露出的新候选项，以及对请求范围有实质影响但尚未审查的关系。对之后出现的候选项适用[范围与授权](#确定范围与授权)。只要还有安全、已获授权且有具体维护收益的改动，就继续；不要求每一轮都重新扫描整个仓库。

评估净维护收益，把新增的抽象、间接层、配置或耦合计算在内。不为了统一而归并，也不引入维护成本超过收益的抽象。

只有在审查范围内已没有任何可被证明既安全又有实质收益的精简、已实施的改动通过了适用的验证，且没有实质性的未决候选项或验证缺口妨碍这一结论时，才报告在当前约束下达到了精简基线。说明审查的边界和实际生效的约束；这不是全局最优的证明。

没有新的证据、关系变化或可执行的工作时，不重复没有变化的调查。未解决的证据、额外的授权或环境限制妨碍进一步判断或验证时，保留受影响的内容，并报告部分完成和具体的限制。停止调查并不确立精简基线。

## 与其他技能配合

- 独立搜索有用时，使用[仓库并行调查](../investigate-repo/SKILL.md)。子代理只返回事实；删除与保全的判断由负责执行的一方作出。
- 范围内需要专门的固定文档维护时，使用[项目文档维护](../maintain-project-docs/SKILL.md)。
- Agent 行为或 `AGENTS.md` 层级确实需要维护时，使用[项目规则维护](../maintain-agent-rules/SKILL.md)。
- 清理会改变可见文案时，建议使用[界面文案清理](../simplify-interface-text/SKILL.md)；它需要用户主动调用，且不在本技能保全行为的范围之内。

只在用到另一个技能时才读它。它的默认做法不扩大清理范围，也不授权新的政策。有界的任务不要求计划、合同、子代理或新的工作树。

## 报告结果

概述：

- 删除、归并或有意保留了什么，以及原因。
- 每一类受影响的义务如何继续得到保护。
- 实际执行的验证及其结果。没有运行的检查与通过的检查分开列出，按套件或文件列明，并说明实质性的未验证范围。

把已确认的冗余及其处置，与未决的候选项、需要额外授权的改动、环境或验证限制区分开。说明这些是否妨碍得出基线结论，并指出已完成的较窄范围。保留一个未决的候选项，既不证明它必要，也不证明它冗余。

既有的验收缺口要保持明确。只审查的工作，不把拟议的改动说成已实施或已验证。
