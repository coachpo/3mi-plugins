# 变更控制

给出变更提案、应用已获同意的提案时遵循本文件。提案只读；应用只在用户同意该提案之后进行。

## 变更类型

按新旧条文允许的范围归类，不按用户用的词：

| 类型 | 判据 | 索引的变化 |
| --- | --- | --- |
| `relax` | 新范围包含旧范围：原来合规的仍然合规 | 编号不变，改陈述 |
| `modify` | 新范围比旧的窄，或范围不变、只是澄清 | 编号不变，改陈述 |
| `replace` | 新旧互不包含 | 旧条目标为 `superseded`，新条目用新编号，两者互相指向 |
| `remove` | 不再约束 | 条目标为 `retired` |

用户说的类型与判据不符时，按判据归类并在提案里说明。例如把“只用 PostgreSQL”改成“只用 MySQL”是替换，不是放宽。

## 影响分析

只读。范围较大时复用[仓库并行调查](../../investigate-repo/SKILL.md)。

1. **定位条文**：出处原句，以及全部重述位置。重述不只看 `Also in`，还要在文档和规则文件里搜索同一条约束的其他说法。
2. **关联条目**：引用它的条目；与拟改条文矛盾、重复，或因此变得多余的条目。
3. **仓库现状**：只用静态证据，不运行、不测量；判断不了就写明判断不了。
   - 新条文更严或换了方向时（收紧的 `modify`、`replace`），现有代码、配置或文档是否已经违反它。违反不阻止变更，但要列出。
   - 旧条文被放宽或取消时（`relax`、`remove`、`replace`），哪些测试、CI 检查、工具配置或代码在强制或依赖它。只列出，不改。
4. **外部义务**：条文或出处表明它出自法律、合同、许可或供应商限制时，写明从文档里放宽或删除并不改变义务本身。决定仍由用户做。

## 提案

在对话里按下列顺序给出，不写入任何文件，不分配变更编号：

1. 变更类型和对象：条目编号，或尚未收录的条文。
2. 现行条文：每个受影响位置的原句和文件位置，逐字引用。
3. 拟改条文：每个位置改成什么，或删除。
4. 理由：用户给出的；没有就写未说明，不代拟。
5. 索引的变化：条目改后的样子，以及将追加的变更记录。
6. 后续项：强制或依赖旧条文、但不在本次改动内的代码、测试和配置。
7. 分析中发现的矛盾和判断不了的地方。

一份提案可以包含多项变更，逐项列出；用户可以只同意其中几项。

## 应用

1. **复核提案是否过期**：重读提案引用的每一处现行条文和相关条目。与提案引用的不一致，就停下说明差异，重新提案。
2. **检查他人改动**：Git 仓库里，受影响文件有不属于本次变更的未提交改动时，报告并询问，不覆盖。
3. **留快照**：受影响文件都与 `HEAD` 一致时，`HEAD` 就是快照；否则，或不在 Git 仓库里，把这些文件复制到仓库之外的临时目录。
4. **改条文**：出处和每个重述位置。只改这条约束的那几句；删除后留下的空列表项或空小节一并清掉，不动相邻内容。出处是 ADR 时不改写原决策，按项目的 ADR 惯例标注它已废止或被取代，没有惯例就在该 ADR 的标题下加一行状态说明。
5. **改索引**：条目和关系字段，最后追加变更记录。
6. **核对**：按[核对清单](constraint-index.md#核对清单)检查索引；重读每处改动；搜索确认没有遗漏的重述；确认差异只落在提案列出的位置。
7. **失败时恢复**：任何一步做不下去，就把受影响文件恢复到快照，本次变更新建的文件删除，只动这些文件；然后报告失败在哪一步、现在处于什么状态。不留下只改了一半的变更。成功后删除临时快照。

## 搁置与裁决

用户要先搁置一处矛盾时，把相关条目标为 `disputed`，以 `Conflicts with` 互相指向，记一条 `dispute`。用户裁决后，按结果走上面的某一类变更；裁决是原样保留的，恢复为 `active`，删去 `Conflicts with`，记一条 `resolve`。
