## 0.3.1 · 根规则模板与用户级指令对齐 · 2026-11-19

对照 Codex 用户级 `AGENTS.md` 检查了根规则模板：模板不引用用户级文件，各节自带判据。据此修订两处措辞，只改了根规则模板。

| 对照发现的问题 | 修订 |
| --- | --- |
| 凭据一节只把 `live` 标记识别为生产或真实账号凭据，比同一模板的环境一节和用户级指令少 `prod`、`production` | 补成三个标记 |
| “项目有效授权规则”没有定义，没有用户级指令的环境里可能把操作手册当作授权 | 写明它指已加载的项目指令或其明确指定的授权来源政策；README、示例或操作手册描述的流程不构成授权 |

已验证：

- Claude Code 的 `claude plugin validate plugins/repo-craft` 和 `claude plugin validate .` 均通过（2.1.322）。前者报两条警告：`ICON_MISSING` 同前；`ARCHIVE_OS_METADATA_FILE` 指本机磁盘上的 `.DS_Store`，该文件已被 `.gitignore` 排除，不在提交内容中。
- 两份插件清单均可解析，版本同为 0.3.1。

未验证：

- 没有重做模板的全量写入与逐条合并样例。已按旧模板初始化的项目再次维护时，凭据一行是改写而非新增，预期会作为冲突逐条询问，这一点没有试验。
- 0.3.0 列出的未验证项仍然未验证；其中 Claude Code 安装后的加载与调用控制已在下一小节实测。

### Claude Code 安装后实测

在 Claude Code 2.1.322 上，对从市场安装的 `repo-craft@coachpo` 0.3.1（用户级，已启用）做了实测。安装缓存中的 `skills/` 与仓库源码逐文件相同。

已验证：

- **技能加载**：新开的无界面会话（`claude -p … --output-format stream-json`）的初始化事件列出三个技能 `repo-craft:investigate-repo`、`repo-craft:maintain-docs-and-rules`、`repo-craft:polish-prompt`，以及子代理 `repo-craft:repo-researcher`，插件路径指向 0.3.1 的安装缓存。
- **`polish-prompt` 不接受模型调用**：交互会话中提供给模型的技能清单只有 `investigate-repo` 和 `maintain-docs-and-rules`。模型用技能工具直接调用 `repo-craft:polish-prompt` 被宿主拒绝，报错写明原因是 `disable-model-invocation`，须由用户自己运行。
- **`polish-prompt` 接受用户主动调用**：在无界面会话中以 `/repo-craft:polish-prompt 把这段初稿改成可交接的任务：“只读排查重试为何失效。”` 调用，一轮内返回：一个只含提示词的代码块（标为草稿）、Codex 和 Claude Code 各一行强度建议（均标暂定）、以 `问题：` 开头的待决事项。期间没有任何工具调用，初稿中的任务没有被执行。
- **`repo-craft:repo-researcher` 可被委派**：主 agent 把一个限定在 `plugins/repo-craft/` 的只读问题委派给它，它返回了带文件路径和行号的结论、冲突和未搜索范围。主 agent 重新打开了其中关于 `disable-model-invocation` 所在行的证据，相符。它实际使用的工具只有 `Read`、`Grep`、`Glob`，并自报没有运行命令或写文件的工具。

未验证：

- `investigate-repo` 和 `maintain-docs-and-rules` 安装后的自然语言触发率，以及技能正文在安装后路径下的完整行为。
- Codex 侧安装后的全部行为。

## 0.2.2 · 第二轮试跑与措辞修订 · 2026-11-19

### 0.2.1 的试跑

在同一个项目的同一分支上，由同一个执行者按 0.2.1 的正文接着重写，用户指示不变。复核了实际产物：

- 改动只涉及 Markdown，暂存区为空。两份模板共 47 条条款逐字出现在目标文件的同名小节内，顺序不变；已从模板删除的小节不在文件里。
- 项目专有规则并入了对应的模板小节，模板条款在前；两份根文件的一级标题是项目标题。
- 架构文档从 575 行收敛到 139 行，契约级细节拆成 8 篇专题文档；38 个 Markdown 文件的 199 个相对链接和锚点全部可解析，引用的脚本名和文件路径都存在。
- 子目录规则从 2 个变为 5 个，每条都是一句指出具体错误的操作规则并带链接。抽查其中引用的三个标识，均在源码中。
- 抽查专题文档的两条事实，均与源码相符。

没有核实：专题文档的初稿被执行者自己的审计查出约 30 处错误或不精确，改正后的文本没有再审一轮，这里也只做了上述抽查；执行者给出的一处出处行号与实际文件不符；文档里的项目命令均未实际运行。

0.2.1 修订表中的八项，在这轮产物里都能看到对应的效果。

### 本版修订的措辞

| 试跑指出的问题 | 修订 |
| --- | --- |
| “在模板之外只补充项目规则”与“写在模板小节之内”矛盾 | 改为“除模板条款外” |
| 例外条款里关于“文件里已有规则”的一句放在了目标不存在的情形下 | 移到非空文件一条 |
| 同主题小节内能否用下级标题、标题下能否加引言、拿不准是否同主题时怎么办，没有说 | 逐项写明 |
| 技能没有给出核对模板写入的方法 | 写明按条款比对，并说明何时才逐字节一致 |
| “契约级细节”只有例子没有判据 | 定为调用方、数据或恢复行为所依赖的事实；纯版式和内部实现机制不写 |
| 专题文档的切分、命名和入口没有约定 | 一个主题一篇，沿用项目命名，从架构文档链接即算有入口 |
| 子目录规则没有下限，且与“不复制贡献政策”有张力 | 约束只在该子树内成立才写；一句操作规则不算复制，理由留在链接的文档里 |
| ADR 日期不可核实时怎么写，含糊 | 不写日期；无法核实的外部理由保留并标注 |
| 只读调研子代理读不了只存在于 Git 历史中的文件，不可用时怎么办没有说 | 历史中的文件由主 agent 查；不可用时用宿主默认子代理并写明只读边界 |

本版只重跑了打包检查，没有再做试跑，上表右列的效果未经验证。文档语言仍然没有规定，这是有意保留的。

## 0.2.1 · 真实项目试跑与修订 · 2026-11-19

### 0.2.0 的试跑

在一个已有约 4900 行英文文档和五个 `AGENTS.md` 的真实项目上，让一个只读技能源码的独立执行者依次运行 `maintain-project-docs` 和 `maintain-agent-rules`。用户明确要求覆盖旧文档、全部用中文，因此“已有有效内容不整篇替换”“取代旧文档前先确认”两处以用户指示为准。写入发生在专用分支，没有提交。这是按源码路径执行，不是安装后的路由。

复核了实际产物，而不只是执行者的报告：

- 改动只涉及 Markdown，暂存区为空。根 `AGENTS.md` 和 `CONTRIBUTING.md` 的开头与两份模板逐字节一致。

### 试跑暴露的问题与本版修订

| 问题 | 修订 |
| --- | --- |
| 根规则模板第一节“共享实现与联动检查”只适用于多入口的插件仓库，却必须逐字写入 | 从模板中删除该节 |

| 子目录规则的两个判据结论不同 | 以“只读父级会做错什么”为准，子树特有的约束也可写进子文件 |
| 项目的业务约束没有归属 | 归贡献指南，根规则只链接 |
| ADR 没有命名和结构约定；“生产标识”没覆盖无生产部署的情形 | 补上 ADR 约定和无生产部署时的写法 |
| “用户已说明的规则取代模板条款”是否包含旧文件里的规则，含糊 | 写明只指用户在对话中的陈述 |
| 旧运维手册中无法核实的内容如何处理，没有规定 | 保留时标注为未核实 |

本版的修订只重跑了下面“已验证”一节中的打包检查，没有再做试跑。因此上表右列的效果未经验证；“模板逐字节一致”这一条在新规则下只对没有项目专有内容的文件成立。

## 0.1.0 · 初始验证

将插件复制到一个只含这一个插件的临时本地市场，另建相互独立的项目样例。未安装或启用插件。

### 打包与宿主发现

- 对五个技能分别运行 Skill Creator 的 `python3 -B quick_validate.py <技能目录>`，五项均通过。另行解析清单、市场条目和调用策略，检查名称与目录一致、包内相对链接可解析、无指向包外的运行资源；用 `cmp` 确认项目级模板副本与输入逐字节一致。
- 运行本机 Codex CLI 0.167.0 的 `app-server --stdio`。子进程使用空白临时用户目录，禁止联网、读取真实用户文件（CLI 程序自身除外）及写入样例区以外的文件。完成握手后，向 `plugin/list` 传入临时市场根目录和 `marketplaceKinds: ["local"]`，实际找到 `repo-craft@coachpo`。
- 用临时市场清单路径及 `pluginName: "repo-craft"` 调用 `plugin/read`：显示名为 **Repo Craft**，`installed: false`、`enabled: false`。返回的五个 `repo-craft:` 技能名和源码路径与包内五个 `SKILL.md` 一一对应。这是宿主发现验证，不是安装后执行。

### Codex 行为试验

让独立 Codex 执行者按**搬移后的技能文件路径**处理请求。写入只发生在隔离样例；复核了答复、调查证据、前后文件树和实际产物，而非匹配技能中的措辞。

| 场景 | 观察结果 |
| --- | --- |
| 润色含写文件指令、用词尚待用户决定的初稿 | 返回独立可复制的草稿、一个待确认问题和两个宿主各自的执行强度。目标目录仍为空。 |
| 并行调查宽度的导入、导出是否无损 | 调查主 agent 与一个子代理并行分查两个方向，汇总前重读四个文件。以乘 1000 后取整和固定三位小数输出给出精度损失反例，并指出合法输入精度未知。样例前后相同。 |
| 为验证入口不同的模块维护规则 | 保留根文件的人工索引约定；仅为 reader、writer 添加局部规则，各自的 `make verify-layout`、`npm run verify-wire` 实际通过。没有给共享常量目录写规则，也没有将缺少测试目录的根命令列为可用步骤。另一个样例的人工发版规则要求 `make attest`，但 Makefile 没有这个目标；执行者保留原文并提问，没有拿 `check` 或 `verify` 代替。 |
| 初始化空项目和不完整项目，再维护一次 | 空项目恰有五个零字节文件和空 ADR 目录；已有项目保留 README 原文，补入经过运行的导出示例以及指向架构、旧投影说明的入口，旧说明和代码未变。无新证据再运行，两棵文件树的路径和文件内容均未变。 |
