# 验证记录

## 0.4.0 · 新增项目约束管理技能 · 2026-11-19

新增技能 `constraint-manager`：正文加两份参考文件（约束索引格式、变更控制）。它只管限制产物的项目约束，不管工作流程规范；只有用户点名的条目才进 `CONSTRAINTS.md`；删除、修改、放宽和替换先给提案，用户同意后才应用，应用只改出处条文、重述位置和索引。不带脚本。

`maintain-docs-and-rules` 的正文改了四处，使它与约束索引并存：

| 位置 | 修改 |
| --- | --- |
| 文档表与“不算旧文档”的清单 | 登记按需存在的 `CONSTRAINTS.md`：本技能不创建它，不建占位，不增删条目，不改条目的状态和陈述；它不算旧文档 |
| 旧文档取代一段之后 | 被索引引用的条文在取代、迁移或拆分文档时保持含义不变，同一次改动中更新索引里的链接；拟舍弃或改写的内容是现行约束时不动它，交给约束管理 |
| “找不到佐证不等于人工约束失效”一句之后 | 已收录的条文，本技能不改含义和条目状态 |
| 核对与交接 | 项目有约束索引时，核对现行条目的链接和所指条文 |

合并规则和另外两个技能没有改动。两份模板的改动不来自本技能：`af9305c` 从根规则模板删去提交、推送和修改 PR 须有授权的条款，从贡献指南模板删去默认新增测试的要求，随本版一起发布；这些改动没有重跑样例。插件 README、仓库根 README、两份插件清单和市场清单的描述随之更新。

### 样例试跑

隔离的 Git 项目：一个带 FastAPI 后端和 React 前端的小应用，十来份文件。约束分散在 README、根目录的旧设计说明、一份 ADR、两篇 `docs/` 文档、贡献指南的项目专有小节和子目录规则里；其中两条各在两处出现，一处缓存选型互相矛盾，另有只体现在依赖清单里的现状，以及 `make attest`、`make check` 两条流程规范。样例的 `AGENTS.md` 和 `CONTRIBUTING.md` 取自试跑当时工作区里的两份模板，再各加项目专有内容；当时工作区的模板已带有 `af9305c` 的改动（那时尚未提交），下面的结论不依赖模板条款的具体措辞。

Claude Code 2.1.322 的无界面会话（`claude -p`，模型 `claude-sonnet-5-5`，`--permission-mode acceptEdits`）以 `--plugin-dir` 加载本版源码，用 `--add-dir` 给出对插件目录的读取授权，不加载 MCP 服务，另放行只读的 Git 命令。多轮场景用 `--resume` 续接同一会话。初始化事件显示插件路径是源码目录，四个技能都已加载。全部运行都带写入权限，“没有写入”指执行者能写而没有写。产物用 `git status`、`git diff` 和两个临时脚本核对：一个按索引格式的核对清单检查编号、字段、状态和关系，一个解析相对链接和锚点。机器的用户级指令和设置照常加载，没有隔离。共 38 次运行，这是按源码路径执行，不是安装后的路由。

### 入口补一句后的重测

上面的试跑里，不带“约束”二字的变更请求首轮都不调用技能。根 `AGENTS.md` 入口因此补了一句：用户要求新立约束，或要改的正是某条约束本身时，用 `constraint-manager` 技能给出提案。用本技能重新建了带新入口的索引，再在它的副本上各跑一次：

| 提示 | 结果 |
| --- | --- |
| 把后端内存上限放宽到 200 MB | 2 次都在第一轮调用技能，给出 `relax` 提案，CI 阈值列为后续项，没有写入。其中一次续跑答复“同意”：只改了出处、重述和索引，变更记录带原条文，CI 里的 100 没有改动，索引通过核对 |
| PostgreSQL 那条不要了，删掉吧 | 调用技能，给出 `remove` 提案，没有写入 |
| 把后端的数据库访问改成 MySQL：换驱动、改连接串 | 没有调用技能，停下并指出冲突的条目，提出可以经技能修改约束，没有写入 |
| 给 /notes 接口加一个按标题搜索的 q 参数 | 没有调用技能，照常实现，并说明改动不触及内存上限 |

## 0.3.6 · 局部规则入口与 Claude Code 的遮蔽条件 · 2026-11-19

对照官方文档和本机会话记录核对了各宿主加载项目规则的方式，有两处差异与本技能有关：

- 子目录 `AGENTS.md` 的加载时机不同。Claude Code 在用 Read 打开该目录里的文件时按需加载；Codex 的发现到工作目录为止，从仓库根启动后不会自动读到工作目录之下的规则文件。此前的模板和技能正文都不要求根文件给出入口，局部规则是否被读到取决于执行者是否自己写了入口。
- Claude Code 自 2.1.277 起原生读取 `AGENTS.md`，但默认只在工作目录及其上级没有 `CLAUDE.md`、`.claude/CLAUDE.md` 或 `CLAUDE.local.md` 时读取，也不读 `AGENTS.override.md`。项目里出现这类文件后，Claude Code 读不到整套 `AGENTS.md`，其他宿主照常读取，没有任何提示。

修订：

- 根规则模板在“贡献指南”之后新增“局部规则”一节，一条条款：修改某个子目录里的文件前，先读该目录到仓库根之间各级的 `AGENTS.md`；宿主已自动加载的不必重读。
- 技能正文“项目规则”首段补一句，写明上面的遮蔽条件，并要求发现这类文件时在报告中指出哪些宿主读不到哪些规则。

贡献指南模板、合并规则和另外两个技能没有改动。

## 0.3.3 · 两份模板之间调整条款归属 · 2026-11-19

把 Codex 用户级 `AGENTS.md`、宿主基础指令和两份模板放在一起逐条对照归属。判据沿用技能正文：根规则只写会改变 Agent 操作的规则，设计、兼容与迁移、提交格式和业务约束属于贡献指南。据此在两份模板之间搬移三处，给贡献指南模板补四条用户级已有的工程规则，在根规则模板加一条指向贡献指南的入口，并给合并规则补上条款换了文件时的处理。

| 条款 | 调整 |
| --- | --- |
| “运营背景”一节 | 从根规则模板原样移到贡献指南模板，排在“设计与实现”之后。它约束设计假设和分析范围，与“设计与实现”中的强制义务一条是同一主题；项目确定的经营主体或市场也随之写进贡献指南 |
| 根规则模板“操作授权”中的“只包含相关改动，保持提交可独立审查” | 移到贡献指南模板“提交约定”，作为第一条。根规则保留提交授权、交接时报告哈希和非快进拒绝的处理 |
| 根规则模板“环境与数据操作”中的“不做分阶段或可回滚迁移、回填、双读双写或保留数据的转换” | 根规则只保留对非生产环境的操作：删除、重置、重灌种子，不为保住数据做备份或演练，不先确认。迁移的实现形态写成贡献指南模板“兼容与迁移”的新条款，并限定为只有非生产数据受影响时 |
| 贡献指南模板“设计与实现” | 新增四条：复用已有代码和依赖，只为具体问题引入抽象；改动只包含必要的内容，不夹带无关清理；设计或审查公共 API 时从调用方的角度评估；注释只解释不自明的理由，不复述代码、不记变更历史 |
| 根规则模板新增“贡献指南”一节 | 一条入口：设计、实现、运营背景、兼容与迁移、验证、界面文案、提交和 PR 的约定在项目根目录的 `CONTRIBUTING.md`，该文件存在时做相应工作前先读对应小节。条款带“该文件存在时”的条件，只做规则、项目没有贡献指南时也成立；路径写成行内代码而非链接，模板文件自身不含失效链接 |
| 模板写入与合并新增“规则属于另一份模板” | 目标文件里与另一份模板条款等义的规则，或一条规则里的某项要求，在对方文件已有后从目标文件删除。整个小节都属于另一份模板时，小节里的项目专有内容一并移过去。对方文件不在本次范围时只报告。没有这条，按旧模板初始化的项目再次维护后会在两份文件里各留一份 |

按本地技能源码在隔离项目验证。一个项目没有目标文件，另一个已有两个零字节目标；只读审查均未写入。初始化后，两处的根规则与贡献指南分别与对应模板逐字节一致，其余四个固定文档仍为空，ADR 目录无占位文件。再次维护时文件树和内容均未变化。

非空样例中，两个技能都先补入无冲突部分，列出冲突并等待选择。逐项答复后，根规则保留禁止提交的原约定，替换快照交接政策；贡献指南采用英文提交描述但保留中文 PR 正文。两份文件中的项目专有规则未变，等义的不可逆操作确认没有重复。

## 0.1.0 · 初始验证

将插件复制到一个只含这一个插件的临时本地市场，另建相互独立的项目样例。未安装或启用插件。

### 打包与宿主发现

- 对五个技能分别运行 Skill Creator 的 `python3 -B quick_validate.py <技能目录>`，五项均通过。另行解析清单、市场条目和调用策略，检查名称与目录一致、包内相对链接可解析、无指向包外的运行资源；用 `cmp` 确认项目级模板副本与输入逐字节一致。
- 运行本机 Codex CLI 0.167.0 的 `app-server --stdio`。子进程使用空白临时用户目录，禁止联网、读取真实用户文件（CLI 程序自身除外）及写入样例区以外的文件。完成握手后，向 `plugin/list` 传入临时市场根目录和 `marketplaceKinds: ["local"]`，实际找到 `repo-craft@coachpo`。
- 用临时市场清单路径及 `pluginName: "repo-craft"` 调用 `plugin/read`：显示名为 **Repo Craft**，`installed: false`、`enabled: false`。返回的五个 `repo-craft:` 技能名和源码路径与包内五个 `SKILL.md` 一一对应。这是宿主发现验证，不是安装后执行。

### Codex 行为试验

让独立 Codex 执行者按**搬移后的技能文件路径**处理请求。写入只发生在隔离样例；复核了答复、调查证据、前后文件树和实际产物，而非匹配技能中的措辞。

| 场景 | 观察结果 |
| --- | --- |
| 润色含写文件指令、用词尚待用户决定的初稿 | 返回独立可复制的草稿、一个待确认问题和两个宿主各自的执行强度。目标目录仍为空。 |
| 并行调查宽度的导入、导出是否无损 | 调查主 agent 与一个子代理并行分查两个方向，汇总前重读四个文件。以乘 1000 后取整和固定三位小数输出给出精度损失反例，并指出合法输入精度未知。样例前后相同。 |
| 为验证入口不同的模块维护规则 | 保留根文件的人工索引约定；仅为 reader、writer 添加局部规则，各自的 `make verify-layout`、`npm run verify-wire` 实际通过。没有给共享常量目录写规则，也没有将缺少测试目录的根命令列为可用步骤。另一个样例的人工发版规则要求 `make attest`，但 Makefile 没有这个目标；执行者保留原文并提问，没有拿 `check` 或 `verify` 代替。 |
| 初始化空项目和不完整项目，再维护一次 | 空项目恰有五个零字节文件和空 ADR 目录；已有项目保留 README 原文，补入经过运行的导出示例以及指向架构、旧投影说明的入口，旧说明和代码未变。无新证据再运行，两棵文件树的路径和文件内容均未变。 |
