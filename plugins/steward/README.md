# Steward

Steward 为 Codex 与 Claude Code 提供仓库精简、界面文案清理、任务指令改写、项目文档与仓库调研技能。两个宿主读取同一份 `skills/` 目录。

## 安装与调用

Codex：

```bash
codex plugin marketplace add coachpo/3mi-plugins --ref main
codex plugin add steward@coachpo
```

Claude Code：

```bash
claude plugin marketplace add coachpo/3mi-plugins@main
claude plugin install steward@coachpo
```

安装或更新后，新建 Codex 任务或 Claude Code 会话加载技能。Codex 调用形式为 `$steward:<skill-name>`，Claude Code 为 `/steward:<skill-name>`。

`analyze-change-request`、`simplify-repository` 和 `simplify-interface-text` 在两个宿主都仅允许显式调用：Codex 使用 `agents/openai.yaml` 的 `policy.allow_implicit_invocation: false`；Claude Code 使用共享 `SKILL.md` 的 `disable-model-invocation: true`。该 Claude Code 扩展字段不替代 Codex 的调用策略；Codex 运行时可加载带该字段的技能，但仅接受通用 frontmatter 字段的校验器会拒绝它，须另用宿主原生加载检查确认兼容性。两宿主的调用控制分别见 [Codex 技能配置](https://learn.chatgpt.com/docs/build-skills#optional-metadata)与 [Claude Code 技能配置](https://code.claude.com/docs/en/skills#control-who-invokes-a-skill)。

## 技能用途与边界

| 技能 | 主要结果与边界 |
| --- | --- |
| [refine-task](skills/refine-task/SKILL.md) | 改写工程需求，不执行原任务；每次都分别给出 Codex 和 Claude Code 的推荐强度，不切换模型。 |
| [simplify-repository](skills/simplify-repository/SKILL.md) | 显式调用；联合精简代码、测试、文档及其他产物，保全行为、覆盖、有效知识和必要用途／保留义务。可独立实施与验证；实施请求即授权删除范围内已纳入版本控制的内容，删除未纳入版本控制或被忽略的文件前须先确认。审查只返回发现，不借清理下线功能、改写政策或重建文档体系。 |
| [simplify-interface-text](skills/simplify-interface-text/SKILL.md) | 显式调用；按角色和状态在渲染出的屏幕上走查界面文案，清理重复、常驻、讲内部机制和解说控件的文字，保留确认、唯一信息和有功能的文字。审查只返回发现；清理按已确认的清单进行，请求点名的文案视为已确认，没有清单时先产出清单并等待确认；清理会改变可见输出，但不改命令、金额、存储事实或服务端契约。不负责新功能文案、翻译或视觉改版。 |
| [analyze-change-request](skills/analyze-change-request/SKILL.md) | 结合仓库与公开来源分析变更需求，提供引用及可观察验收标准。显式调用；只读，不实施或执行项目。 |
| [parallel-repository-research](skills/parallel-repository-research/SKILL.md) | 至少两条独立调查线定位代码、梳理架构或追踪依赖，主代理核实证据。调用即授权范围内的只读委派，用户显式调用和被自动选中时相同。只读，不运行测试或判定行为风险。 |
| [write-agent-guides](skills/write-agent-guides/SKILL.md) | 维护有依据的 AGENTS.md 层级，共享规则在根文件，子树仅记录局部差异。仅在用户要求或新建根 AGENTS.md 时写入默认政策。仓库指南不依赖用户级全局指令文件：只读取它们以发现冲突并报告。不维护 CLAUDE.md、技能或子代理提示词，也不编辑用户级全局指令文件。 |
| [write-project-docs](skills/write-project-docs/SKILL.md) | 按仓库事实和既有约定维护正式项目文档，明确权威来源并同步相关链接。新建或迁移且仓库没有既定布局时使用默认文档集合；仅在用户要求或新建贡献指南时写入默认政策。局部更新不扩展为文档套件。 |

Codex 可以按意图隐式选择任务指令改写、仓库调查、项目文档和代理指南技能；其他技能保持各自的调用策略。审查请求只返回发现；创建、修改请求在指定范围内落盘；`simplify-repository`、`simplify-interface-text`、`write-agent-guides` 和 `write-project-docs` 在请求未说明审查还是修改时按审查处理。Claude Code 版另带只读调研插件 agent `steward:steward-researcher`，用法见下文的只读调研一节。

## 仓库精简

使用 `simplify-repository` 清理已证实冗余的仓库内容，目标是只保留仍有用途或保留义务的内容，而不是让每类内容都减少。它拥有独立的文档归并和产物清理职责，其他文档技能提供专门方法，不排除这些清理范围；迁移、业务历史、许可证、测试基准和必要交付输入不能仅因陈旧或可重新生成就删除。

有界清理无需先建计划、任务合同、子代理或工作树。

```text
使用 $steward:simplify-repository 精简当前仓库的代码、测试、文档及其他产物，保全四类义务并完成验证，不提交或推送。
使用 /steward:simplify-repository 只审查当前目录的冗余候选及保留义务，不实施清理。
```

## 界面文案清理

使用 `simplify-interface-text` 清理已有界面上不改变用户行动、也不提供新信息的文字。重复和冗余只在渲染出的屏幕上成立，所以先按角色和状态走查，再对照已确认的清单清理；到不了的状态从源码读取并注明。为复现页面状态，可在非生产环境创建并推进带标记的测试记录，请求本身即覆盖这一步；生产环境需要用户针对该环境的指示，审查时不在生产环境创建。审查不修改源码、文案、配置或既有记录。规则优先取项目贡献指南中已采纳的界面文案规则，没有时使用默认的界面文案原则。保存在实例里的设置或内容不是源码，单独列给内容所有者。它与 `simplify-repository` 的区别是会有意改变可见输出。

```text
使用 $steward:simplify-interface-text 审查顾客端和员工端的界面文案，给出带页面、出现条件和源码位置的清单，不修改源码、文案、配置或既有记录。
使用 /steward:simplify-interface-text 对照已确认的清单清理界面文案，所有语言同步，完成验证，不提交或推送。
```

## 交付链路

一次代码变更可按下列链路使用技能；每一步都可单独调用，不需要的步骤可以跳过。

1. `analyze-change-request` 在对话中给出带来源和验收标准的需求分析，复杂仓库搜索配合 `parallel-repository-research`；由用户确认需求和决策。
2. 开发与验证由宿主按用户当前授权直接完成。
3. 变更影响文档时，用 `write-project-docs`、`write-agent-guides` 同步正式文档与代理指南；任务运行态不写入这些文档。

## 模型分工

技能不改会话或调研 worker 的模型与 effort 设置，沿用用户或宿主配置。`refine-task` 只在改写结果中分别给出 Codex 和 Claude Code 的推荐强度。

## 项目文档

文档维护沿用项目的语言、路径、信息结构和政策。新建文档，或在没有既定布局的仓库里迁移时，使用默认文档集合：`README.md`（用途、上手、链接）、`STATUS.md`（持久的生命周期、部署、支持、用户、数据和兼容事实）、`CONTRIBUTING.md`（开发环境、命令、流程、完成检查，以及设计、开发和评审政策）、`docs/PRODUCT.md`（用户、目标、范围、需求、流程、验收，以及运营主体、运营地、首发市场和义务）、`docs/ARCHITECTURE.md`（现有组件、职责、依赖、数据流和设计决策）。每份文档只在其创建条件成立且有已核实内容时创建，不为凑齐集合建空文档；已有路径和权威划分优先。写入、更新或迁移文档时，仅在授权范围内对照当前代码、配置和已采纳决策校正本次请求涉及或影响的架构文档，范围外偏差只报告，纯措辞或链接修改不要求架构审查。用户要求写入或补齐项目政策，或请求新建贡献指南或其他权威政策文档时，记录乐观设计原则，以及保持源文件内聚、易导航并在规模妨碍理解或评审时拆分的开发原则。`write-agent-guides` 在用户要求或新建根 `AGENTS.md` 时将这些原则转为项目根 `AGENTS.md` 中的可执行约束，详细政策与理由链接贡献指南等已有权威文档。仓库源码确有面向用户的界面文字时，贡献指南另外记录界面文案原则：同屏只说一次、正常状态不提示、不讲内部机制、不解说控件，同时保留确认、唯一信息和有功能的文字；语言、单位、术语和具体例外按项目事实写，没有界面的仓库不写入。`write-agent-guides` 在根 `AGENTS.md` 只写一条短规则；有权威章节则链接，没有则只写规则、不加链接，也不因此新建贡献指南。已有文档中有用的内容、翻译和托管标记予以保留；有仓库生成器管理的区域遵循其契约。默认政策的单一来源是插件级的 [references/default-policies.md](references/default-policies.md)，三个技能共用。

用户要求写入或补齐项目政策，或请求新建根 `AGENTS.md`、贡献指南或其他权威政策文档时，两个文档技能补齐其中缺失的政策章节，并在相关章节明确写入“本项目默认不保留向后兼容”，已有等价表述不重复；其他权威文档已写明的政策不重复写入。对这些文档的其他改动不补写，只报告缺失。请求只写其他项目文档时不补写也不报告；只写子树 `AGENTS.md` 时不补写，只报告根文件的缺失；审查请求报告缺失。用户或当前有效项目规格、政策明确要求兼容时遵循该要求。默认不为旧接口、格式、配置或实现保留兼容层、别名、双轨路径及过渡代码；获授权替换实现时，同步更新相关调用方、配置、派生契约、测试及文档，移除不再需要的旧路径，不因“可能还有旧调用方”自动增加旧字段回退、双读双写或格式转换。清理限于当前任务；这项文档默认值不自动授权删除现有兼容代码或修改公共 API。`write-project-docs` 将政策写入贡献指南或已有权威政策文档；`write-agent-guides` 将可执行规则写入根 `AGENTS.md`，子树继承，范围外缺失只报告，审查请求仍只读。

兼容政策同时说明迁移代码的处理：没有生产部署迹象时，迁移不必保留已有数据或历史，可以重写、合并或重新生成；有生产部署时，会在生产运行的迁移必须对生产正确，已发布的迁移不重写、不合并。`write-agent-guides` 在根 `AGENTS.md` 内联写明部署状态和生产标识：数据库、部署目标、分支、域名，以及生产或真实账户密钥所在的变量名或文件名，不写密钥值。两个文档技能按默认政策中的同一条规则判定部署状态：用户或已采纳的项目文档说明，或仓库里有部署配置、CI 部署任务、生产环境文件、发布记录等迹象时，写为有生产部署；没有这些迹象且用户未另作说明时，写为没有生产部署，并注明这是基于缺少迹象的工作假设，以及哪些迹象会触发重新判断。清单不是穷尽的，未列出的目标带有生产标记时仍按生产处理。这项默认值不自动授权重写现有迁移。

默认政策另有一节说明非生产数据与密钥，属于代理操作规则，只由 `write-agent-guides` 完整写进根 `AGENTS.md`（不压成短规则，因为没有别的文档可链接），`write-project-docs` 不写进贡献指南：除非能认出是生产，否则环境及其数据按非生产处理，数据可直接 drop、truncate、重建或重新灌种子，不做备份、dry run、分阶段迁移、双读双写或保留数据的转换；除非能认出是生产或真实账户密钥（带 live 标记、来自生产配置或环境文件、来自工具凭据存储、主目录配置或 shell profile、项目清单列出，或用户说明是生产或个人密钥），否则按测试密钥直接传递，不确认、不加密、不重新编码；不为存密钥单独建文件，已落盘的用 `0600`，任何密钥都不提交、不写进日志或报告；生产环境的每次破坏性或迁移操作、每次使用生产密钥都需要用户明确指示。这一节只免除非生产数据操作的确认，不授权提交、推送或部署。

默认政策还有一节授权与 Git，同样只完整写进根 `AGENTS.md`：回答、审查、诊断、规划类请求只读，变更类请求授权范围内的本地修改和验证；提交、推送、PR 变更、发布、部署、其他外部写入、购买、破坏性操作和实质范围扩展需要用户或项目指引的明确授权；合并或开启 auto-merge、强推、使用生产或真实账户密钥、生产环境的破坏性或迁移操作只能由用户针对具体对象授权，项目指引、CI 通过、review 批准或“继续”都不算；push 被拒绝时报告而不强推；委派不扩大授权。

默认政策还包括两条设计原则和两组有条件的内容。围绕核心业务流程和业务结果正确性确定范围，不主动加入当前阶段不必要的需求。已确认适用的强制要求即使不阻塞核心流程也纳入需求或设计约束，适用性未确认不等于不适用。仓库是在运营的产品（有产品文档，或用户说明）时，另外记录运营背景原则：运营主体、运营地或首发市场未确定时不作假设，按市场中立设计；已知运营地只是业务背景，不等于要求做本地化或合规分析；只在用户要求，或为遵守已接受的约束、判断或履行与当前工作相关的强制义务时，才对特定市场做有限核查。运营主体、运营地、首发市场以及已确认和未确认的义务是项目事实，由 `write-project-docs` 写进产品文档。仓库没有既定的 commit 或 PR 约定时，记录默认约定：Conventional Commits 格式的标题，以及含 Summary、Changes、Testing、Notes 的 PR 描述；PR 部分只写给使用 pull request 的仓库。这些约定不授权提交、推送或开 PR。

任务进度、执行记录和证据属于 working state，不写进 AGENTS.md、README、status、其他正式文档或源码注释。跨压缩／跨会话工作遵循根 working-state policy，使用 gitignored 的 `.agent-work/<task-slug>/`，保存的命令与输出中的密钥值以占位符替换；项目状态只维护持久事实，事实变化时就地改写，不承载进度、changelog、计划或日期工作日志。

恢复任务时先检查历史验证是否仍适用，以及命令的当前目标、环境、副作用和任务授权；仅在需要且仍获授权时重跑。未重跑时保留历史结果并注明未重新验证，历史命令本身不构成执行授权。

```text
使用 $steward:write-project-docs 更新 README 中受本次变更影响的用法与链接。
使用 $steward:write-agent-guides 维护 packages/api/AGENTS.md 的局部命令差异。
```

## 只读调研

变更分析区分用户要求、实际约束和待决定建议，按目标版本核实代码与公开来源，并随用户纠正更新受影响证据。公开查询不携带私有源码、秘密或个人数据。

仓库调查使用宿主可用的委派工具。Claude Code 使用插件 agent `steward:steward-researcher`：只有读文件和搜索工具，只读由工具限制保证，Git 历史由主代理自己查。Codex 和其他宿主沿用默认 worker，不指定模型。子任务限定在仓库读取，主代理核实决定性证据；调用 `parallel-repository-research` 或 `analyze-change-request` 即授权范围内的只读委派，显式调用和被自动选中时相同；委派不可用或用户限制时直接调查。并行能力不会扩大权限；在 Codex 和宿主默认 worker 上，只读仍只是提示词约束，不构成操作系统隔离。

```text
使用 $steward:analyze-change-request 分析批量导入需求，给出来源和验收条件，不修改文件。
使用 $steward:parallel-repository-research 调查两个独立服务的重试调用链，给出代码证据。
```

## 授权边界

技能遵循当前任务授权，发现技能不等于授权执行。实施请求允许范围内的本地准备、修改和验证；计划内容获批不自动授予执行或所有交付动作的权限。提交、推送、PR 变更／合并、发布、部署、外部写入、购买、破坏性操作和实质范围扩展需要相应明确授权；已经成立的授权可以继续使用，不重复确认。授权实施、提交、归档和删除本次任务工作树／分支时直接完成这些动作，不扩大到主会话、集成分支、无关来源会话或业务数据。

Codex Desktop 仅在用户明确要求新 chat 时使用相应创建工具；工作树会话遵循用户选择和实际工具规则，异步创建需取得真实 ID 后再协调。CLI／Claude Code 使用实际可用执行者和 Git 工作树，不强制安装额外插件。宿主有可恢复工作树归档机制时优先使用，必要的 ignored 材料另行保存；工作树清理与会话归档是两个操作，工具或权限缺失时如实报告保留状态。
