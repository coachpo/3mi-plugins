# State and evidence model

## Durable authority

Kernel `0.4.0` initializes journal schema 4 and artifact manifest schema 1. A campaign root contains the append-only journal, atomic state and summary projections, a single-runner lock, and immutable attempt/case-run directories. Each finished case-run contains `result.json`, `stdout.txt`, `stderr.txt`, declared evidence, and `artifact-manifest.json` with `artifactManifestVersion: 1`.

The journal is authoritative. Its initialization binds the kernel, journal, and artifact-manifest versions. Journal schema 4 retains the normalized optional trace inputs, declared digests, case-to-criterion/invariant/finding mappings, every Review finding's required flag and immutable case-candidate digest, and any Review attestation introduced by schema 3. For strict Review input it also retains the full canonical request, its adapter-pinned digest, and `bindingsVerified: true`; attestation without that triple is compatibility evidence, not strict input. Entries bind the catalog and source fingerprints, immutable run identity, state transition, and case artifact manifest/hash. Schema 4 additionally binds the complete source snapshot at attempt start and the complete fixed-source snapshot in `fix_recorded`; every present entry contains path, size, mode, and SHA-256, while a deleted path has explicit missing status. Replay recomputes the exact added, modified, deleted, and mode-only project-source delta and requires exact equality with sorted `changedFiles`, with `changedFilesVerified: true`. Source-inventory control files remain visible in the snapshots, and additions or removals from that inventory become project-source delta entries rather than disappearing from proof. A strict post-fix handoff is appended as `review_handoff_recorded`, including the fresh full request, request digest, and verified binding, not inferred from a mutable projection. If that exact pending binding is later disproved before retest, `pending_fix_superseded` records the fix ID, previous fixed-source fingerprint, optional Review-manifest digest, observed replacement fingerprint, and validated drift reason before allowing another fix audit. Sequence numbers, the hash chain, event shape, and transitions must all replay exactly.

Projections are replaceable views, not evidence. A mutating command acquires the lock and may rebuild a missing or stale projection from a valid journal before continuing. It never truncates or invents journal history. Malformed or semantically invalid history is a configuration/state error, not a repair opportunity.

Before an attempt or case start event is appended, POSIX runners durably synchronize the new allocation and its parent directories. Windows runners first try `FlushFileBuffers` on a no-reparse directory handle; filesystems that do not support directory flushing use a stable directory-identity barrier while retaining the journal file's strict flush. This Windows fallback preserves platform usability but provides weaker abrupt-power-loss guarantees than POSIX directory `fsync`.

The lock serializes campaign state only. Maintain one campaign runner and one project-fix writer; it does not lock the project worktree, devices, services, or other processes.

Journal schema 2 and 3 campaigns created by kernels `0.2.0` and `0.3.0` are supported read-only. `status` and `audit` replay them under their pinned schema without upgrading or rewriting them; `run`, `record-fix`, `record-review`, `supersede-fix`, `retest`, and `resume` refuse mutation and require a new journal-schema-4 campaign root. Their older records do not carry schema-4 attempt/fixed snapshots and therefore provide no machine proof that a declared `changedFiles` list is complete; status or audit compatibility must not imply otherwise. Schema 1 standalone journals remain unsupported legacy inputs and receive the same no-mutation/new-root diagnostic.

## Status semantics and recovery

Case execution starts at `PENDING`, records `RUNNING` before launching, and ends as `PASS`, `FAILED`, `BLOCKED`, or `INTERRUPTED`. A passing targeted retest records `RETEST_PASSED`. A drifted regression attempt records `INVALIDATED`.

- `PENDING` means not yet attempted. Cases after the first fail-stop remain `PENDING`.
- `NOT_RUN` is reserved for an optional case unsupported on the current platform or transitively unrunnable because an optional dependency was legitimately `NOT_RUN`. It must retain and report the exact platform or dependency reason.
- `FAILED` covers a nonzero command, assertion failure, timeout, product/test defect, or success-path evidence-contract failure.
- `BLOCKED` covers a missing required platform/prerequisite, a safety violation, or an integrity condition that prevents trustworthy execution. It does not imply that the same root is resumable: only a temporary prerequisite restorable on the pinned runtime host gets the one bounded same-mode retry. A required-platform blocker or runtime-platform mismatch cannot be repaired in that root; preserve it and initialize a new root on the correct host only within the original authorization, without consuming the old root's retry.
- `INTERRUPTED` preserves a started run that did not reach a valid terminal record.

Journal schema 3 adds `quick` attempts. They execute only adapter cases marked `quick: true` and preserve their outcomes and artifacts under separate `quickStatus` projection fields; after a successful quick attempt the campaign remains `PENDING` and full case status remains untouched. A quick result alone is history only: it does not advance full initial coverage, produce `READY_FOR_REGRESSION`, establish a final regression attempt, resolve a required finding, or satisfy criterion/invariant coverage. A quick failure may still be diagnosed, bound to `failedRound: "quick"`, fixed, and targeted-retested; the resulting history still requires ordinary initial execution and clean regression, which rerun quick-marked cases as part of the full catalog.

`resume` converts an active run to durable interruption evidence and allocates a new run linked to the predecessor. If a process stops after creating an empty attempt or case allocation but before its start event is durable, the next mutating operation reconciles only that structurally valid empty shell; non-empty, linked, or ambiguous objects remain rejected. An interrupted or recoverably blocked retest resumes under the same current fix binding and its recorded Review handoff. The bounded retry applies only after restoring a temporary prerequisite on the same pinned runtime host; never spend it trying to move a campaign across platforms. If the restored condition blocks once more, retain `BLOCKED` and stop. If a retest fails, clear the old pending fix atomically and require a new fix audit; an attested campaign must then produce a new Review at a different source-excluded path inside the operation's frozen write set. If source drifts after a strict `record-fix`, or its recorded Review manifest is verified stale before retest, `supersede-fix --fix-id <exact pending id>` appends `pending_fix_superseded`, clears only the active projection, and preserves the old fix/handoff as superseded history. The next `record-fix` remains bound to the same latest failed attempt and current observed source, and the next Review must use a distinct path. The command rejects a wrong ID, no pending fix, unchanged source plus valid handoff, legacy campaign, or authority/catalog drift. If a successful retest clears its fix binding before a crash, resume initial coverage from the saved checkpoint; later Review drift requires a new campaign root rather than this bounded pending-fix transition.

During initial execution, source drift is not a pass and requires a new campaign root. During regression, any source drift preserves the attempt as `INVALIDATED` and leaves the campaign `BLOCKED`, regardless of whether traceability mode is `none`, `legacy`, or `attested`. The changed source is never adopted as a new baseline and the kernel never starts another regression automatically. Inspect the actual diff, preserve the old root, and initialize a new root only within the original authorization; do not add an outer retry loop. An attested campaign also has a stale effective Review, but that does not create an in-place refresh path.

Trace inputs are independently observed from the paths and digests pinned at initialization. Trace content, path identity, contract version, request target or requested paths, or canonical digest drift is never a new acceptable baseline within the same campaign. A request-bound attested Review additionally binds the complete source fingerprint, scoped file hashes, GOAL/invariant digests, and exact requested scope; `REVIEW_BASELINE_DRIFT` identifies a stale Review baseline. Status exposes `traceabilityMode`, `traceInputDrift`, and `traceInputErrors`; `traceabilityMode` is exactly `none`, `legacy`, or `attested`. Attestation-only input remains `legacy`; only an exact request/pin/verified binding is `attested`. Ordinary mutating commands fail closed, and audit returns `TRACE_INPUT_DRIFT`. The one bounded exception is the authorized repair transition: after source-changing repair, a strict campaign may preserve the stale initial Review as historical evidence only long enough to record the fix and bind a fresh Review. It may not retest or complete from that stale Review. A trace document that also appears in the source inventory remains subject to both trace and source drift rules.

The public `validate-adapter`, `status`, regression, `resume`, and `audit` result envelopes expose `executionStatus` and `completionStatus`. Validation reports `NOT_EVALUATED`/`INCOMPLETE`; campaign results preserve the legacy journal `status` field and mirror it as `executionStatus`. A successful regression command or regression-completing `resume` is `AUDIT_REQUIRED` because that execution response did not evaluate audit. A current successful audit is `COMPLETE`; a current failed audit is `INCOMPLETE`, or `BLOCKED` when the journal itself is blocked, and never remains `AUDIT_REQUIRED`. `status` performs that same current audit computation. Every `audit.ok: false` result has at least one stable `rejectionCodes` value. `status` and `resume` expose the journal-derived `resumeMode`, which is the continuation authority: in schema 4 quick PASS transitions it to `initial`, initial PASS to `regression`, and regression PASS to null, while failed, blocked, or interrupted attempts retain their current mode. `currentMode` alone is not a recovery instruction. A completed campaign treats `resume` as an idempotent observation; it never reruns regression or replaces the required audit.

## Artifact integrity

The case artifact manifest binds the relative path, byte size, and SHA-256 of `result.json`, both output streams, and every recorded evidence file. The journal binds that manifest. Audit rejects an added, missing, changed, symlinked, reparse-point, or non-regular artifact and verifies agreement among journal, projection, result, manifest, and disk.

Successful `PASS` and `RETEST_PASSED` runs must satisfy the complete evidence contract. A genuine `FAILED` or `BLOCKED` run may record required business evidence as missing because that absence can be the failure fact; the manifest and result must still describe the missing state consistently, and every file claimed as present must verify. Historical valid failures therefore remain auditable after a later fix and successful regression.

Each stdout and stderr stream persists at most 5 MiB while the runner continues draining excess output. `truncated` records size truncation independently from `secretDetected`; ordinary large output is not a secret. Persist only sanitized output, and preserve failed, blocked, interrupted, and invalidated artifacts.

A case-run may contain at most 4,096 artifact entries and 256 MiB in total; no single artifact may exceed 256 MiB. Exceeding a bound is a safety `BLOCKED` result with bounded, auditable evidence rather than an unbounded read.

## Fix binding and completion

Create a fix audit from [`../assets/fix-audit.template.json`](../assets/fix-audit.template.json). Bind it to the latest unresolved failed case, round, attempt, failed source fingerprint, and current fixed source fingerprint. State the proven root cause, smallest repair, changed files, and focused retest evidence. Under schema 4, `record-fix` compares the failure-attempt snapshot with a newly observed fixed-source snapshot and requires `changedFiles` to be the exact complete project-source delta, including additions, content changes, deletions, and mode-only changes; omissions, extras, duplicates, or post-observation change are rejected. An empty changed-file list requires `externalCondition: true` plus evidence that the condition was restored. Recording a fix proves the declared change set, not that the repair works; retest and final regression remain required.

For trace-enabled work, the enhanced fix record also contains:

- `violatedInvariant`: normally the triggered hard-invariant ID whose violation explains the defect; the failed case must already cover it. If and only if the failed case covers no triggered invariant, use `{ "notApplicable": true, "technicalReason": "..." }` to preserve truthful recoverability without inventing an invariant.
- `rootCauseSource`: an exact project-source location object `{ "path", "lineStart", "lineEnd", "symbol"? }`. The normalized path must be a regular non-link file in the source inventory, lines are one-based and in bounds, and `symbol` is an optional trimmed single-line name. Point to the source of the root-cause conclusion, rather than only the symptom or failing-test message.
- `resolvedFindingIds`: unique review-finding IDs linked to the failed case that this repair actually resolves; an empty list makes no resolution claim. A finding owned only by another case cannot be claimed by this fix.
- `permanentGuardrail`: either `{ "kind", "sourcePath", "caseId", "evidenceFile" }` or `{ "notApplicable": true, "technicalReason": "..." }`.

A concrete guardrail's `kind` is one of `test`, `guard`, `rule`, or `adversarial-case`. Its `sourcePath` must still exist as a regular non-link project source file in the final source inventory and fingerprint. Its `caseId` must name a required adapter case that covers the violated invariant and every claimed resolved finding, passes the final full regression, and verifies the declared non-empty `evidenceFile`. A not-applicable disposition is exceptional and requires a specific technical reason; it is not shorthand for deferring the guardrail. Campaigns without traceability continue to accept the legacy fix shape; omit the four enhanced fields because a legacy fix makes no invariant, finding-resolution, or permanent-guardrail claim.

If the initialized Review has an attestation plus an exact pinned request binding, the repair lifecycle is strictly:

```text
record-fix -> fresh read-only Review -> authorized canonical handoff
           -> record-review -> retest -> same-source full regression -> audit
```

The independent Reviewer does not write or execute anything. The coordinator may persist its canonical `view` only under existing project-write authorization, at a distinct regular non-link path outside `campaignRoot` and excluded from the source fingerprint. `record-review` requires a closed `FAILED` campaign with a pending fix; it revalidates the manifest against the fixed source, pinned GOAL and invariants, initialized finding IDs, required flags, case-candidate bindings, and trusted expected request. A source target is deterministically rebound to the fixed source. A diff target requires `--expected-review-request` with the same kind, base identity, and requested paths, the fixed source fingerprint, and a freshly pinned head identity; the handoff manifest cannot nominate that expected identity itself. The event journals the manifest digest, full request and digest, verified binding, source/authority digests, outcome, scope hashes, finding states, and fix ID. The Review must be complete, and each finding claimed in `resolvedFindingIds` must now be `resolved` or `invalidated`. Retest and every later execution phase re-read the effective manifest, canonical digest, request, scope, source, and authority bindings; a changed or missing excluded handoff never stays executable merely because the source fingerprint is unchanged. Retest refuses a strict campaign without that event. Existing v1 campaigns without a pinned request retain the legacy `record-fix -> retest` path, but their journals cannot prove that a fresh semantic Review covered the exact requested target and scope.

A required review finding has resolved final proof only through a linked required case that passes final regression. Every historical `FAILED` run of that resolving case must be bound to a fix whose `resolvedFindingIds` contains the finding ID; a final-passing case with no historical failure needs no invented fix record. This prevents an unrelated passing case or an unbound repair from closing the finding.

Final acceptance requires both:

```text
RequestedCoverageSatisfied ∧ audit.ok
```

Requested coverage includes all required cases and all runnable optional cases in one final regression on a shared source fingerprint. `coverageMode: "full"` is mechanically valid only when required cases represent all five risk tiers; optional-only tiers cannot satisfy it. `coverageMode: "narrow"` permits a smaller requested catalog, but its normalized coverage report keeps every absent required tier in `missingTiers` and `outOfScopeTiers`; narrow `audit.ok` never means full coverage. Status and audit derive `verifiedTiers` only from required cases that pass the successful final regression and list declared-but-unproven required tiers in `unverifiedTiers`. For trace-enabled campaigns requested coverage additionally requires a required-case final-regression `PASS` mapping for every required GOAL criterion and every triggered hard invariant from the shared loaders, a required-case link for every required review finding, resolution of every required finding according to its contract and active fix history, a required final-regression `PASS` case for every declared required scenario, and verification of every active concrete permanent guardrail. Attested campaigns additionally require an immutable handoff for every non-superseded fix and require the newest effective Review source fingerprint to equal both the current source and final-regression source. A superseded fix remains append-only history but is not an active completion or guardrail obligation; audit reports whether its historical handoff remains available without allowing that stale record to replace the latest valid handoff. Audit requires replayable history, matching projections, complete immutable artifacts, no unresolved fix or active/failed/blocked/interrupted attempt, unchanged catalog, unchanged applicable Review handoff, and unchanged final source. Quick, initial `PASS`, and `RETEST_PASSED` results are history, not final regression proof.

## Stable audit rejection codes

Audit exposes sorted stable identifiers in `rejectionCodes` and detailed coverage in its `traceability` object. Treat each code as the machine contract and the accompanying `errors` message as explanation.

| Code | Rejection |
| --- | --- |
| `TRACE_INPUT_DRIFT` | A referenced GOAL, invariant, or review-finding contract no longer matches its pinned path, version, or digest. |
| `REVIEW_REQUEST_REQUIRED` | A strict Review or diff handoff lacks its separately pinned expected request binding. |
| `REVIEW_REQUEST_MISMATCH` | The manifest request, adapter/event pin, initialized target, fixed source, or trusted post-fix request does not agree exactly. |
| `REVIEW_HANDOFF_REQUIRED` | A request-bound campaign fix lacks its required post-fix Review handoff. |
| `REVIEW_HANDOFF_INCOMPLETE` | A post-fix Review has structured gaps or leaves a fix-claimed finding open. |
| `REVIEW_HANDOFF_DRIFT` | A post-fix manifest, digest, scope, finding/candidate binding, authority binding, path, or current-source binding is invalid or stale. |
| `SOURCE_BASELINE_MISMATCH` | The final-regression source differs from the current observed source, or in an attested campaign the effective latest Review source differs from either one. |
| `CRITERION_UNCOVERED` | A required GOAL criterion lacks a mapped required `PASS` case in the final full regression. |
| `INVARIANT_UNCOVERED` | A triggered hard invariant lacks a mapped required `PASS` case in the final full regression. |
| `REQUIRED_SCENARIO_UNCOVERED` | A declared `failure`, `compatibility`, or `platform` scenario lacks a tagged required case that `PASS`es final full regression. |
| `REQUIRED_FINDING_UNLINKED` | A required review finding is not linked by any required adapter case. |
| `REQUIRED_FINDING_UNRESOLVED` | A required review finding remains unresolved under the loaded review contract and recorded fix history. |
| `GUARDRAIL_MISSING` | A trace-enabled fix lacks both a valid concrete guardrail and an explicit not-applicable disposition. |
| `GUARDRAIL_SOURCE_UNBOUND` | A concrete guardrail source is absent from the final bound source inventory. |
| `GUARDRAIL_CASE_NOT_FINAL_PASS` | The concrete guardrail case is absent or does not `PASS` in the final full regression. |
| `GUARDRAIL_EVIDENCE_MISSING` | The guardrail's named evidence file is absent, empty when required, or not verified in its final case artifact. |
| `FULL_REGRESSION_REQUIRED` | Quick history exists but no successful final full regression is available. |
| `RETEST_WITHOUT_FULL_REGRESSION` | A successful targeted retest exists without a later successful full regression on the final baseline. |
| `FINAL_REGRESSION_REQUIRED` | No successful final regression is available. |
| `REQUIRED_CASES_INCOMPLETE` | A required or runnable optional case lacks final-regression `PASS`. |
| `EVIDENCE_INCOMPLETE` | Final-regression evidence is missing or empty under its declared contract. |
| `ARTIFACT_INVALID` | One or more campaign artifacts fail their exact tree, type, size, or digest contract. |
| `CATALOG_DRIFT` | The current adapter catalog differs from the initialized catalog. |
| `SOURCE_OBSERVATION_FAILED` | Audit cannot safely establish the current source identity. |
| `SOURCE_CHANGED_DURING_AUDIT` | Source identity changes during the audit stability check. |
| `JOURNAL_PROJECTION_MISMATCH` | `state.json` or `summary.json` differs from authoritative journal replay. |
| `DUPLICATE_FINAL_BASELINE` | More than one successful regression claims the current final baseline. |
| `UNRESOLVED_STATE` | Campaign execution, a pending fix, or the final attempt remains unresolved. |
| `AUDIT_INCOMPLETE` | Audit is incomplete but no more specific stable rejection applies. |
