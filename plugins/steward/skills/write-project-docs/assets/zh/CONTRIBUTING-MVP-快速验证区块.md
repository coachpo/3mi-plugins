### MVP 快速验证

本阶段以验证 [`{{PRODUCT_DOC}}`]({{PRODUCT_DOC}}) 中已确认的核心假设、范围、非目标以及可观察的验收与退出条件为目标，优先实现能够产生有效证据的最小可观察闭环。“最短”是获得可信反馈的路径最短，不是代码、步骤或测试最少。

本小节是 MVP 启用态对“通用设计原则”和“通用实现原则”的范围覆盖：只把直接服务上述核心验证的工作纳入本轮，不为完整性扩展范围。

**明确不做：** 与核心假设、可观察验收和退出条件无关的安全/隐私专项治理、权限体系扩建、数据完整性增强、兼容层建设与全量兼容回归、可达风险专项治理、仓库级全量检查和生产加固，以及不影响当前验证结论的附加功能与非主路径业务分支。已有兼容承诺和仓库必需检查本身不属于该分类，也不构成排除授权；只能排除其非核心专项实现、全量验证或默认门禁。已有兼容承诺仍限制方案选择，受影响路径或核心验收所需检查仍执行。

**可推迟：** 当前不影响验证结论、但出现真实用户、真实或不可丢弃数据、外部流量、兼容验收、相应风险或其他可观察触发条件时应重新纳入的工作。每项都必须写明事项、当前推迟依据和至少一个可观察重评条件；没有重评条件且与核心验证无关时归入“明确不做”，会影响当前结论时纳入当前闭环。

**仍是约束：**

- 不扩大权限；
- 不执行未授权外部写入；
- 不执行未授权破坏性操作；
- 不删除或重置现有数据；
- 不虚构验证结果；
- 不主动违反 [`STATUS.md`](STATUS.md) 的明确禁止事项。

这些约束限制可选动作，但不自动增加专项实施或全量检查。

在该收窄范围内，设计与实现仍遵循上文各自的选择顺序；多个方案都能完成核心验证时，优先选择改动范围小、新增依赖少、容易观察和撤销的方案。局部、低风险、可逆且不改变授权边界的实现细节，可在既有权限和开发工作流内直接决定。

只实现当前验证所必需的能力，不为未验证需求增加通用化能力、抽象或依赖；运行足以让验证结论可观察、可复现的窄验证。非核心的仓库级全量检查、默认门禁和生产加固不作为完成前提，但受影响路径或核心验收明确要求的检查仍执行；不得把未经验收的验证性实现表述为正式架构或生产能力。
