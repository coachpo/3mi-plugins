# 源代码规模与职责规则

## 目的

本规则用于约束手写源代码的职责边界和可维护规模，帮助开发者及 Coding Agent 在实现功能时保持既有架构、避免职责扩散，并在文件继续增长前主动审查结构。

行数只触发审查，不做判定。是否拆分由「职责自检」的结果决定：自检通过的长文件可以保留，自检不通过的短文件同样应当拆分。任何拆分都必须改善职责、依赖方向、可测试性或变更隔离；不得为了满足数字而破坏内聚性。

本规则的行数按物理行计算，以 `wc -l` 等常规工具的结果为准。行数只用于决定何时触发审查，不需要更高精度。

## 适用范围

本规则适用于承载业务行为、交互行为、状态管理、编排、适配、数据访问或基础设施行为的普通手写源文件。

以下内容不直接套用普通行为文件的规模信号和职责自检，但仍应保持清晰、可审查并遵守项目架构：

- 自动生成且能由确定流程重新生成的代码；
- 数据库迁移和不可分割的历史演进记录；
- schema、协议、目录、映射表和其他以声明数据为主的文件；
- 第三方或 vendored 代码；
- 测试快照、固定样例和大规模测试数据；
- 因完整叙事或端到端流程而保持内聚的集成测试。

不得通过把行为代码伪装成配置、宏、回调、生成代码或数据表来规避本规则。

## 职责自检

职责自检是本规则的判定门禁。三问都不要求理解完整业务逻辑，读取文件头部、导出符号和调用关系即可回答，并且每一问在不通过时都直接指出拆分边界。

**一、职责能否单句表述**

能否用一句不含连词（和、与、以及、`and`）、不依赖 `utils`、`helpers`、`common`、`core`、`base`、`manager`、`misc` 之类空泛词的名词短语，说清该文件的主职责？

不通过时的拆分边界：必须用连词才能说清，连词两侧即为两个职责，按其边界拆分；只能用空泛词命名，说明该文件尚未形成职责，应把其中的符号按真实归属分别移入对应模块。

**二、依赖是否跨层**

文件的 import 是否只跨越 `{{ARCHITECTURE_DOC}}` 允许的层？同时直接依赖传输框架、持久化实现、领域模型和外部 SDK 的文件，无论长短都已经跨层。

不通过时的拆分边界：越层的那组依赖及其调用代码即为应当抽出的部分，抽入允许的层，或建立具有明确接口的新模块。

**三、导出面是否内聚**

文件中各导出符号的调用方集合是否存在重叠？若符号 A 与符号 B 的调用方完全不相交，二者不属于同一职责。

不通过时的拆分边界：按调用方集合分组，互不相交的分组即为拆分边界。

若某文件因可验证的结构原因长期无法通过某一问，把该例外及其理由记录在 `{{ARCHITECTURE_DOC}}`；例外不得改写本通用规则。

## 规模审查信号

- 文件达到约 240 行时，提前检查其主职责、依赖方向和自然拆分边界，避免在后续需求中被动膨胀。
- 普通手写行为文件超过 300 行时，执行一次职责自检。三问全部通过即可继续，不需要在变更说明中补充论证；任一问不通过，按该问指出的边界拆分。
- 函数或方法达到约 50 行时，检查是否混合了多个阶段、抽象层、错误处理策略或副作用。保持较长函数时，应能说明其连续性和可测试边界。

这些数字只决定何时触发审查，不决定是否拆分。它们在不同语言中对应的逻辑密度差异很大，不得当作上限执行。

## 职责与拆分原则

- 每个文件应有一个可清楚表述的主职责和主要变更原因。
- 依照领域边界、模块边界、状态生命周期、输入输出边界或副作用边界拆分。
- 入口、组合根和路由层应保持轻薄，主要负责装配、调度和边界转换；不为它们设置脱离项目事实的统一行数上限。
- 新职责应放入已有正确模块，或建立具有明确接口的新模块；不得把方便访问当作放置依据。
- 抽取后应减少认知负担，并保持或改善依赖方向、命名、测试和错误处理。

禁止以下机械拆分：

- 按行数切成 `part1`、`part2` 或含义不明的同级文件；
- 把无关逻辑集中到通用 `utils`、`helpers` 或“公共”模块；
- 增加只做透传的包装层、代理层或无业务含义的接口；
- 通过嵌套回调、宏、配置或生成步骤隐藏复杂度；
- 仅移动代码而不形成新的职责边界或测试边界。

## 遗留大文件

- 已存在的大文件不因数字本身自动成为无关变更的重构目标。
- 修改遗留大文件时，不得继续加入新的独立职责。
- 判断是否存在自然拆分边界时，变更历史是可验证的依据：若文件中某一区段与其余部分在最近若干次提交中从未一起修改，说明它承担独立的变更原因，其范围即为拆分边界。
- 若本次变更附近存在安全、自然且可验证的拆分边界，应优先抽取该边界并运行适用验证。
- 若拆分会扩大范围、改变行为或缺少验证条件，应保持本次修改局部化，并在变更说明中解释未拆分原因；不得用大规模顺手重构掩盖当前需求。

## Coding Agent 执行要求

开始编码前：

1. 阅读 `{{ARCHITECTURE_DOC}}`、`{{DEVELOPMENT_RULES_DOC}}` 和本规则；
2. 确认目标模块、允许的依赖方向及现有实现；新增文件必须在 `{{ARCHITECTURE_DOC}}` 中有明确的归属模块，没有则先确定模块归属再实现；
3. 检查计划修改或新增文件的当前规模和职责。

编码过程中：

1. 持续检查是否新增了独立职责、跨越架构边界或复制已有能力；
2. 在自然边界出现时及时拆分，不等到文件完成后再机械处理；
3. 保持入口和组合代码轻薄，业务规则留在其归属模块。

完成前：

1. 运行项目适用的测试、静态检查和构建验证；
2. 对本次新增或修改后超过 300 行的普通手写行为文件执行职责自检，列出未通过的文件；如无，明确说明无；
3. 对列出的文件给出将采取的拆分边界，或说明为何在本次变更中保持局部化（见「遗留大文件」）；
4. 确认没有通过机械拆分、无意义抽象或隐藏复杂度规避本规则。
